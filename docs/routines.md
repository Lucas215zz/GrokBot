# 例程（Routines）

例程 = **某个 Bot + 一段指令 + 一个时间表**。到点自动跑，不用你在场。

## 三种触发方式

| 方式 | 配置 | 例子 |
| --- | --- | --- |
| 固定间隔 | `{ kind: "interval", minutes: 60 }` | 每 60 分钟巡检一次 |
| 每天 | `{ kind: "daily", time: "09:00" }` | 每天早 9 点整理待办 |
| 每周 | `{ kind: "weekly", dayOfWeek: 1, time: "08:30" }` | 每周一 8:30 出周报 |

## 怎么创建

界面：「左栏 → ⏰ 例程 → + 新建」，填名称、选 Bot、写指令、选时间表。

## 怎么修改

设置填错了随时可以改，不用删了重建。列表里每条例程右侧都有「**编辑**」按钮：

点「编辑」→ 同一个编辑器会用**当前值回填**（名称、Bot、指令、触发方式、时刻、是否允许危险操作）→
改完点「**保存修改**」即可。取消则什么都不改。

| 你改了什么 | 生效范围 |
| --- | --- |
| 名称 / 指令 / 允许危险操作 | 下次运行立刻用新值 |
| 触发方式 / 时刻 / 间隔 | 保存时**重算 `nextRunAt`**，按新时间表走 |
| 换绑到另一个 Bot | 之后由新 Bot 执行；历史执行记录保留 |

> 执行记录（最近 20 条）不会因为你编辑而清空。正在后台跑的那一轮不受影响 ——
> 想让新设置马上生效，可以先「停止」再「立即运行」。

## 实测证据

创建一条「每分钟巡检」例程，指令是「往 patrol.log 追加当前时间」，
然后**什么都不做**，等一分钟：

```
lastRunAt: 17:12:00
ok: true
durationMs: 16655
steps: 6
summary: "巡检已完成：我已在当前工作目录创建并追加 patrol.log ..."
```

`patrol.log` 内容：

```
2026-10-28 17:12:12
```

全程无人干预，Bot 自己取时间、写文件、读回校验。

## 执行记录

每条例程保留**最近 20 条**执行记录：

```json
{
  "at": 1793178720006,
  "ok": true,
  "durationMs": 16655,
  "summary": "巡检已完成…",
  "steps": 6
}
```

界面上显示「上次 成功 17:13:17」，点「立即运行」可手动触发一次测试。

## 后台执行

「立即运行」是**后台启动**：点完立刻返回，界面不阻塞，同一时间还可以继续聊天或切到别的 Bot。

- 运行中按钮会变成红色的「**停止**」，点一下就能中止当前这一轮
- 状态栏显示「正在后台执行，可以关窗口」
- 执行结束后记录里会标明来源：`manual`（手动）还是 `schedule`（定时）
- 被手动停掉的那次会记为 `stopped`，摘要写「已手动停止」，不算失败

### 关窗口 ≠ 退出程序

点窗口右上角的 **X** 只是把窗口**收进系统托盘**，例程会在后台继续按时间表执行。

| 操作 | 效果 |
| --- | --- |
| 点 X / 关窗口 | 窗口收进托盘，**例程继续跑** |
| 点托盘图标（左键）/ 双击 | 把主窗口叫回来 |
| 托盘右键 →「退出 Grok Bot」 | 真正退出，调度器停止、运行中的例程被中止 |
| 任务栏菜单「退出」 | 同上 |

第一次收进托盘时会弹一次系统通知，避免误以为应用被关掉了。
如果托盘图标加载失败，会退回到「关窗口即退出」的正常行为，不会留下没有界面的僵尸进程。

## 限制与保证

- **每个 Bot 最多 50 条例程**（对齐官方）
- **同一条例程同一时刻只跑一次**：手动触发和定时触发共用一份运行表，不会叠跑；不同例程之间互不影响
- 关掉窗口会收进托盘继续跑，只有**退出应用**才会停（本机模式）；换成云计算机后可 24 小时无人值守
- 失败不会停掉调度，只记录日志
- 应用重启后会重新计算下次触发时间，不会因为关机而漏跑或狂补

## 数据在哪

```
%APPDATA%\Grok Bot\routines.json
```

## 什么时候该用

- 每天固定产出（日报、周报、数据快照）
- 定期巡检（服务健康、磁盘、日志异常）
- 定时整理（收件箱归类、待办汇总）

建议流程：**先手动跑一遍 → 调好指令 → 再挂时间表**。
指令写模糊了，自动跑出来的东西也没法用。

## 和技能的关系

| | 技能 | 例程 |
| --- | --- | --- |
| 是什么 | 「怎么做事」的流程 | 「什么时候做事」的时间表 |
| 触发 | 任务匹配时由模型主动读 | 到点自动跑 |

最佳组合：把重复的事固化成技能，再让例程按时调用它。

## 结果以 `report_result` 为准：杜绝「假成功」

原来的判定是 `ok = 没报错 && 没被中止`，结果是模型只要吐了段文字（哪怕内容是
「我没能完成，原因是…」）就会被记成**成功**。这个坑在小红书采集那条例程里一次踩了 8 次：
8 条全是「无法完成」的文字汇报，日志里却全绿。

现在的约定：

| 情况 | 判定 |
| --- | --- |
| 模型调用 `report_result(status="success")` | `ok = true` |
| 模型调用 `report_result(status="blocked")` | `ok = false`，但界面显示「受阻」（不是崩溃，是需要人介入） |
| 模型调用 `report_result(status="failed")` | `ok = false` |
| **跑完了却没调用 `report_result`** | `ok = false`，摘要写「模型未上报执行结果（未调用 report_result）」 |
| 手动停止 | `stopped = true`，`ok = false`，摘要「已停止」 |

- `report_result` 工具签名：`{ status: "success"|"blocked"|"failed", summary, details? }`
- 只有**例程**（无人值守）会在系统提示里加「结束前必须调用 report_result」这段；
  普通对话不受影响，模型不会被迫做这个。
- `report_result` 属于**安全**操作，不会弹审批。
- 所以写例程指令时，务必明确要求模型「最后用 report_result 上报」，
  否则这条例程永远判失败。指令里也建议写清「成功了报什么、失败/受阻报什么」。

实测：
- `node scripts/verify-routine-report.js` —— success / blocked / failed / 未上报 / 停止 五种情形全绿；
- `node scripts/verify-report-tool.js` —— 工具与循环透传；
- 真实 app 端到端（采集例程）：`ok=true`、`reportStatus=success`、81 秒、5 步完成。
